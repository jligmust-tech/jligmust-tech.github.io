Network topology for multi-agent systems: from blackboards to agent swarms

The swarm survey traced ideas from boids and ant colonies to LLM agent societies. The 500-agents brief treated massive parallelism as an orchestration problem. The collective-hallucination review showed that correlated error, not headcount, decides whether a population is useful. And the context-engineering post described a real system that is a hierarchy with a shared filesystem.

Each of those posts touches the same missing variable: who is allowed to talk to whom. This post isolates it. It defines network topology as the message graph, compares the graphs that keep reappearing, works through the message arithmetic, connects topology to error propagation and parallel scheduling, and places the idea on a timeline from stigmergy to topology-aware evaluation.

Scope note: this is a synthesis and investigation, not a new benchmark. No agent system was run for this post. Message counts are illustrative arithmetic, not measurements; they exclude retries, acknowledgments, broadcasts, and source transfer. Publications are labeled PR (peer-reviewed), PP (preprint), or IND (industry report). The companion posts are linked rather than restated.
Central claim: topology is a design variable with measurable consequences — message count, exposure count, correction path, latency, and merge cost — and it is not the same thing as model choice, prompt quality, or context length. Most “swarms” are star or hierarchy graphs with a scheduler; most “debates” are small complete graphs; many “societies” lean on a shared memory or artifact store. Naming the graph is the first step toward attributing a result to wiring rather than to compute.

1. Why topology deserves its own investigation

Three claims recur in the multi-agent literature and are routinely conflated:

  • More agents help. This is a claim about population size.
  • More interaction helps. This is a claim about the number and arrangement of edges.
  • More diversity helps. This is a claim about the correlation of errors, which topology can either expose or hide.

A result can be true for one and false for the others. A star with 500 workers is a large population with a small interaction graph; a five-agent debate is a small population with a dense interaction graph. Both are called “multi-agent,” and they are not the same experiment. The first is a fan-out problem; the second is a consensus problem.

The distinction also explains why the same benchmark can produce opposite conclusions. If the task rewards breadth and independent retrieval, a star wins because it parallelizes coverage. If the task rewards resolving a contradiction, a small complete graph may win because every agent can see every claim. If the task rewards consistency, a hierarchy may win because the merge is centralized. None of those outcomes is a fact about “swarms” in general.

2. What counts as topology

In this post, topology means the message graph: nodes are agents, tools, or shared stores; edges are the channels through which one node can read, write, call, or observe another. The graph has two kinds of edges, and mixing them is a common source of confusion:

  • Evidence edges carry findings, citations, retrieved passages, or artifacts. They determine what an agent can condition on.
  • Control edges carry assignments, cancellations, approvals, and budget limits. They determine what an agent is allowed to do.

A star coordinator usually has both edges pointing at the hub. A blackboard has evidence edges to a shared store and control edges from a scheduler. A debate has dense evidence edges and almost no control edges beyond a stop rule. The distinction matters because a system can have a dense evidence graph and a centralized control graph at the same time — which is exactly what the Anthropic orchestrator-worker architecture does.

Three further distinctions keep the analysis honest:

  • Logical vs. physical topology. The logical graph is who reads whom. The physical graph is which process, provider, region, or queue carries the request. A logical star can be physically distributed; a logical mesh can run on one machine.
  • Topology vs. model. Changing the graph while holding the model, prompts, tools, and token budget fixed is a topology ablation. Changing all four at once is a product launch.
  • Topology vs. context. Giving each worker a short, isolated context is a context decision. Giving each worker a read edge to every peer is a topology decision. The two interact, but they are not the same knob.

Two rows deserve special attention. The star and its hierarchical variant are the default because they make accounting, rate limiting, and provenance tractable; the cost is a hub that becomes both a bottleneck and a single point of failure. The complete graph is the topology the debate literature implicitly assumes, and it is the one whose message count makes 500 agents impossible: 500 × 499 = 249,500 directed deliveries per round, against 1,000 for a star. The 500-agents synchronization section reaches the same default: exchange compact evidence at explicit milestones, not every thought with every peer.

The blackboard is the quiet one. It looks decentralized because workers do not message each other, but the shared store is a hub with its own consistency problem: a false or stale artifact can be read by every later worker, and “append-only” prevents overwrites without preventing misinformation. The collective-hallucination review catalogues the consequence as emergent shared belief and context fragmentation.

4. Message arithmetic, latency, and the merge

The simplest reason topology matters is that the number of deliveries grows at different rates. For N workers, a round of all-to-all updates is N(N−1) directed deliveries; a star is 2N; a 20-group hierarchy with 25 workers per group is 500 upward submissions plus 20 group summaries = 520 upward submissions, before acknowledgments and broadcasts. These are different communication contracts, not equal-work throughput measurements.

Illustrative arithmetic, not a network benchmark: at 500 workers, a complete graph is 249,500 directed deliveries per round; a star is 1,000; a 20-group hierarchy is 520 upward submissions. The counts say nothing about token cost by themselves, but they bound the coordination surface an operator has to trace.

Latency follows a different shape:

  • Star: roughly the slowest worker plus the hub's reduction and dispatch time. The hub's context and rate limits become the ceiling.
  • Hierarchy: roughly the slowest group plus one or two reduction levels. Local parallelism is preserved, but a slow group delays its branch.
  • Chain: the sum of stage latencies, not the maximum. A five-stage relay has the latency profile of five handoffs and the cost profile of five full contexts.
  • Complete graph: the slowest agent plus the number of consensus rounds. Message cost grows quadratically even when wall-clock time looks acceptable at small N.
  • Blackboard: the slowest write plus the read and merge time. Freshness is a design choice; late evidence can invalidate an early synthesis.

The merge is where topology becomes a system. A distributed-systems merge is a fold with predictable cost. An agent-system merge is usually a language model reading N outputs, which means the reducer inherits the failure modes of an agent: it can be distracted by the middle of its input, accept a confident wrong answer, or silently drop a finding that only one worker reported. A topology that is cheap to fan out but expensive to reduce is not cheap. This is the argument in the parallel-agents timeline review: if the merge is O(N) in human attention, the effective speedup is bounded by reading speed, not concurrency.

The engineering consequence is a preference for mechanical merges — a sort, a count, a filter, a schema check, a vote with a stated rule — over a prose synthesis that hides its evidence. The merge rule is part of the topology because it determines which edges actually carry information into the final answer.

5. Topology and error propagation

Topology is not only a cost decision. In the contagion framing used by the collective-hallucination review, a false claim spreads with R0 = β·k/γ: β is the adoption probability per exposure, k is the number of peers a worker effectively reads, and γ is the correction rate. Topology enters through k and through the correction path.

Topologyk (peers effectively read)Correction pathExpected pressure on R0
Star / coordinator1 for each worker; N for the hubWorker → hub → workersHub adoption dominates; correction is fast only if the hub verifies rather than relays
Chain / relay1 (the previous stage)One hop per stageSlow correction; errors compound with depth and are hard to localize
Complete graph / debateN−1Any peer can contradictHigh exposure and high correction; can still lock in a confident consensus
Debate with judgeN−1 plus the judgeJudge is the final edgeDepends on judge independence; a same-family judge raises β and can launder a shared error
Blackboard / shared storeReadership of the artifactRe-read and revisionPersistent false claims; correction requires explicit invalidation, not just a later correct write

These are qualitative predictions to pre-register, not measured values. Their purpose is to make k and the correction path explicit before the run, so that the R0 comparison is between architectures rather than between slogans.

There is a second, more basic arithmetic. If agents share a model, a prompt family, and a retrieval corpus, their errors are correlated, and the effective number of independent voters collapses:

N_eff  ≈  N / (1 + (N − 1)·ρ)

With ρ = 0.5 and N = 100, N_eff ≈ 2.0: a hundred agents behave like two. Topology cannot fix a shared prior; it can only change how many times the shared error is exposed and whether an independent evidence edge exists. That is why the useful diversity knobs are different retrieval, different model families, and different evidence partitions — not different personas reading the same context.

6. Topology and parallel execution

The 500-agents brief frames the operational problem as synchronization: freeze the brief, assign ownership, keep evidence append-only, check freshness at commit, and define completion explicitly. Each of those choices implies a topology, even when the topology is not drawn:

Synchronization policyImplied topologyWhat it optimizesWhat it risks
Strict round barrierStar or shallow hierarchy with a barrier at each roundConsistent snapshots and simple dependency semanticsOne slow or failed worker delays the whole round
Asynchronous evidence streamBlackboard with reducers building provisional viewsEarly availability and throughputLate evidence invalidates an early synthesis; final release still needs a coverage gate
Hybrid local groups plus milestonesTwo-level hierarchy (groups → root)Less global coordination; local reductionsLocal summaries omit minority evidence; unresolved objections get compressed away
All-to-all debateComplete graph, usually with a judgeMaximal critique at small NQuadratic cost, conformity, and a judge that shares the generator's family

For a 500-worker fleet, the practical default is a star or a shallow hierarchy, with all-to-all reserved for small, high-stakes panels. The reference design already separates planning, execution, evidence handling, and synthesis; topology is the layer that says which of those stages can see which other stage's outputs.

Two failure modes are specifically topological:

  • Hub capture. In a star, the coordinator reads every worker output. Its context becomes the real bottleneck, and its errors become global. A hierarchy reduces this by local reduction, at the cost of summary loss.
  • Stale-edge writes. In any graph with leases, a worker that loses its lease can still return a late artifact. The topology needs a fencing token or snapshot check at the merge edge, not just a prompt instruction. The 500-agents brief's synchronization contract is the operational version of this point.

Amdahl's law and the Universal Scalability Law explain why the speedup curve bends even when the topology is clean: the serial fraction and the coherency cost grow with coordination. The parallel-agents timeline draws the shape — speedup saturates, efficiency falls, and the merge becomes the system.

8. Timeline, 1959–2026

The history has two threads that are often told separately: a coordination thread (how agents share state and assign work) and an optimization thread (how populations search). The LLM wave inherits both, then adds a third: a learned graph. The timeline marks the topology contribution of each period rather than every publication.

  • 1959–1991 · coordination without a controller · contribution: shared state, bidding, local rules
  • 1959Stigmergy — termite construction explained by traces left in the environment; coordination without direct communication, and an ancestor of the modern shared-memory agent system.
  • 1970s–80sBlackboard systems — agents coordinate by reading and writing a shared workspace rather than messaging each other; an early explicit shared-state topology, and the ancestor of the modern artifact store.
  • 1980Contract net — a manager announces a task, contractors bid, and the manager awards it; a market-shaped topology with explicit manager and contractor roles.
  • 1986–87Boids — three local rules (separation, alignment, cohesion) produce flocking; the demonstration that global order needs no global controller.
  • 1991Ant colony optimization — pheromone trails as a distributed memory that solves shortest-path problems; the first swarm algorithm with a real optimization target.
  • 1992–2003 · swarms as optimizers · contribution: cheap, derivative-free search
  • 1995Particle swarm optimization — a population of candidate solutions moved by personal and social bests; two update rules and a decade of applications.
  • 1999–2003Swarm intelligence formalized — the field gets a name, a textbook, and a canon; convergence analysis begins, mostly for simplified variants.
  • 2005Artificial bee colony — the metaphor-first design pattern is established: pick an animal behaviour, map it to an update rule, name the algorithm.
  • 2004–2015 · parallel workers and the metaphor correction · contribution: fan-out/fan-in and baseline discipline
  • 2004MapReduce — fan-out, shuffle, fan-in; the canonical many-worker pattern and the reason “map then reduce” is the default shape of parallel agent work.
  • 2006–14Metaphor proliferation — firefly, cuckoo, bat, wolf, krill, and dozens more; each published with comparisons to older metaphors rather than to strong general-purpose baselines.
  • 2015“The metaphor exposed” — a direct critique that many nature-inspired methods are repackaged local search with extra parameters, and that the naming obscures rather than describes the mechanism.
  • 2015–18Benchmark hygiene — the field converges on tuning budgets, statistical tests across many runs, and comparisons to well-tuned classical baselines; publication volume falls, usefulness does not.
  • 2016–2022 · multi-agent RL and population search · contribution: measurable emergence
  • 2017–19Emergence in MARL — competition and environment shaping produce tool use and niche construction in simple simulated worlds; the interesting result is that the behaviour is fragile and hard to transfer.
  • 2020–22Population-based training and collective search — swarms become an engineering pattern for hyperparameter and policy search rather than a biological metaphor.
  • 2023–2026 · societies of language agents · contribution: coordination in natural language
  • 2023Generative agents, CAMEL, AutoGen, MetaGPT — memory, reflection, role-play, and message passing become frameworks; “society” is implemented as a conversation with a scheduler.
  • 2023Multi-agent debate — the first swarm-adjacent method with a clear metric (factual accuracy) and a clear baseline (the same model alone).
  • 2024Optimizable agent graphs — GPTSwarm and AFlow treat the topology as the thing to search; the swarm becomes an object of optimization rather than a metaphor.
  • 2025Orchestrator–worker at production scale — a lead agent, parallel subagents, isolated contexts, and a shared filesystem; the hierarchy-plus-blackboard pattern becomes the default for breadth-first research.
  • 2025Failure taxonomies and collective bias — agents that never verify, converge on unvalidated plans, and harden arbitrary conventions into norms.
  • 2026Topology-aware evaluation — this review's proposal: report the message graph, measure R0 per topology, and separate wiring from model and compute. The measurement is available; the standard is not.

9. Where 2026 sits

  • Topology is still mostly implicit. Papers name a “multi-agent system” or a “society” and describe the roles, but rarely publish the adjacency list, message count, or correction path.
  • The default architecture is a star or a shallow hierarchy. That is not a failure of imagination; it is what makes accounting, rate limits, provenance, and the merge tractable at scale.
  • All-to-all is a small-panel tool. The quadratic message count is acceptable for five debaters and impossible for five hundred workers; treating it as a general swarm design is a category error.
  • Blackboards are under-examined. Shared memory is the most common persistence mechanism in agent systems and the least measured for stale-read and false-claim propagation.
  • Learned graphs are promising but easy to game. If the topology is optimized against a benchmark, the benchmark becomes a topology prior; the objective needs a held-out task and a compute-matched baseline.
  • The measurable variables are available. Message count, k, correction latency, R0, Neff, merge cost, and coverage are all cheap to record. The field's gap is reporting discipline, not instrumentation.

10. Reporting checklist

If a study claims a multi-agent advantage, the topology should be checkable without reading the code. The minimum set:

  1. Draw the message graph. Nodes are agents, tools, and stores; label evidence edges and control edges separately.
  2. Count the messages. Report deliveries per round and per accepted result, excluding and including retries.
  3. Name the correction path. Who can contradict whom, and how many hops does a correction take?
  4. Report k and R0 per topology. A single R0 for a mixed graph is not interpretable.
  5. Report the merge rule. Mechanical (sort, count, filter, schema check, vote) or model-generated prose? What is the cost per accepted result?
  6. Report the baseline. One strong agent at the same token budget and, where possible, the same wall-clock budget.
  7. Report coverage. Which partitions were accepted, missing, failed, cancelled, or superseded? A response-count quorum is not complete coverage.

This is deliberately unglamorous. It is also the difference between a result and an anecdote: a topology that is not recorded cannot be compared, and a comparison that does not hold the model, budget, and merge fixed is a comparison of products, not mechanisms.

Closing thoughts

The most useful thing about network topology is that it turns a vague claim into a checkable one. “A swarm of agents” becomes a graph with N nodes, E edges, a message count, an exposure count, a correction path, and a merge rule. Those quantities are cheap to record and hard to fake. They also explain why the same architecture can look brilliant on a breadth-first task and useless on a tightly coupled one.

The historical lesson is the same one the first swarm wave learned about baselines: state the mechanism, not the metaphor. A star is not less “swarm-like” than a mesh; it is a different experiment with a different bill. The field does not need another animal name. It needs the graph, the count, and the merge.
